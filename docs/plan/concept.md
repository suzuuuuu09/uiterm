## 開発背景

ターミナルやターミナルマルチプレクサ、AIエージェントなど、開発に利用するツールは多様化している。

CLIは自由度が高く、キーボードで効率的に操作できる。一方、複数のワークスペースやAIエージェントの状態管理など、GUIの方が適している操作もある。

uitermではこれらを無理にCLIまたはGUIへ統一せず、それぞれの利点を活かした開発環境を構築する。

## コンセプト

**CLI First, Not CLI Only.**

- ターミナル・ターミナルマルチプレクサ・ワークスペース管理を統合する。
- CLIの自由度とGUIの利便性を両立する。
- 自分の開発スタイルに合わせて柔軟にカスタマイズできる。
- 日常的に利用しながら継続的に改善できる環境を目指す。

## 設計原則

- CLI First, Not CLI Only：CLIを中心としながら、GUIが適している場面では積極的に使う。
- Lightweight：メモリ使用量・ディスク容量・起動時間を意識する。
- Japanese First：日本語環境での利用を前提として設計する。
- Keyboard First：主要な操作をキーボードのみで完結できるようにする。
- Customizable：ユーザーが自身の開発環境を柔軟に構築できるようにする。
- Cross-platform：macOS・Linux（Wayland）に対応する。
- Minimal by Default：標準状態では必要最小限の機能を提供する。
- Interoperability：既存のCLIや外部ツールとの共存を重視する。

## 技術要件

- TypeScriptをメインの開発言語とする。
- Tauriをデスクトップアプリケーションの基盤とする。
- libghosttyやherdr-coreなど、既存のターミナル関連技術を利用する。
- パッケージ管理にはpnpmを使用する。
- OS固有の処理とアプリケーションの主要機能を分離する。
- 外部サービスやライブラリへの依存を局所化する。

## 操作インターフェース

- GUI・CLI・キーバインド・TypeScriptから共通の機能を操作できるようにする。
- 特定の操作方法に依存しない設計とする。
- 複数の操作を組み合わせて独自のワークフローを構築できるようにする。

## 日本語対応・国際化

日本語対応を追加機能ではなく基本要件として扱う。

### 入力・表示

- 日本語IMEによる快適な入力
- 未確定文字列・変換候補の適切な表示
- 日本語変換中のキーバインド誤作動防止
- 全角・半角文字の正確な表示
- 日本語フォントへのフォールバック
- macOS・Linux間での入力体験の差異軽減

### インターフェース

- 日本語・英語の表示切り替え
- メニュー・コンテキストメニューの多言語対応
- サイドバー・設定画面の多言語対応
- 通知・エラーメッセージの多言語対応
- 将来的な対応言語の追加を考慮した設計
- ユーザー定義のメニューやアクションでの日本語利用

## ワークスペース

Window → Workspace → Tab の階層構造を採用する。

- リポジトリや作業ディレクトリをワークスペースの単位とする。
- 複数のワークスペースを切り替えながら作業できる。
- ワークスペースごとに独立した作業状態を保持する。
- サイドバーでワークスペースとAIエージェントの状態を視覚的に管理する。
- AIエージェントや実行中のタスクへ素早くアクセスできるようにする。

## サイドバー

サイドバーはワークスペースの切り替えだけでなく、作業状況を把握するための領域とする。

- ワークスペース名
- Gitブランチ・リポジトリの状態
- AIエージェントの稼働状況
- ユーザーの操作を必要とするタスク
- ユーザーが定義した任意の情報

表示内容や順序はカスタマイズ可能とする。

## タブ

タブは用途に応じた作業領域とする。

- Terminal：通常のCLI・TUIの利用
- Agent：AIエージェントとの対話・作業管理
- Browser：開発プレビューやWebページの閲覧（検討中）

特定の用途に限定せず、将来的に新しい種類のタブを追加できる構造とする。

## AIエージェント

既存のAIエージェントを自由に利用できる環境を提供する。

- 既存のCLIベースのエージェントを利用できる。
- エージェントの作業状況をGUIで把握できる。
- 入力待ちや承認待ちの状態を確認できる。
- 特定のモデルやハーネスの利用を強制しない。
- CLIとGUIによる操作を必要に応じて使い分けられる。

## カスタマイズ

TypeScriptで宣言的・プログラマブルに設定できるようにする。

- 外観・テーマ・フォント
- キーバインド
- サイドバーの表示内容
- 独自コマンド・アクション
- ワークスペースやタブの操作
- イベントフック
- アプリケーションが提供するAPI・ヘルパー関数の利用
- ユーザー独自の関数定義・再利用
- 型補完による快適な設定ファイル編集

設定値の変更だけでなく、既存の機能やヘルパー関数を組み合わせて、ユーザー自身が動作や機能を拡張できる環境を目指す。

## 軽量性

- 不要なランタイムや依存関係を同梱しない。
- 使用していない機能によるリソース消費を抑える。
- 不要なバックグラウンドプロセスを常駐させない。
- メモリ使用量・ディスク容量・起動時間を継続的に評価する。

## 非目標

- 既存のCLIツールをすべて置き換えること。
- 独自のAIハーネス開発自体を目的とすること。
- 一般的なWebブラウザを置き換えること。
- 多機能であることだけを目的に機能を追加すること。
- CLIまたはGUIのどちらか一方に操作を限定すること。

## 意思決定

- 機能の多さよりも日常的な使いやすさを優先する。
- 独自実装よりも既存技術の利用を優先する。
- 利便性を損なわない範囲で軽量性を追求する。
- 将来の可能性だけを理由に設計を複雑化しない。
- 実際の利用経験に基づいて機能を追加・改善する。
